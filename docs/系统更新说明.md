# 管理端在线更新

在服务器电脑打开 http://127.0.0.1:8768，登录管理员账号，进入“系统更新”。保存仅有本仓库 Contents 和 Attestations 读取权限的 GitHub 下载凭据后，点击“检查更新”，有新版本时点击“更新并重启”。账号、预算数据和已上传底稿保存在原电脑，不通过 GitHub 同步。

## 旧版首次衔接

已有“系统更新”入口的 v2026.09.14.1，先安装 2026.09.23.0 升级组件过渡版。它保留原来的业务程序和数据库结构。网页恢复后，再次点击“检查更新”，安装新的业务版本。无需重新安装系统、重建账号或搬移预算文件。

过渡版与新版均需正式发布后才可检查到；源码提交或草稿发布不会触发安装。没有“系统更新”入口的更早安装仍需单独引导升级。

旧版安装过渡包时沿用原有的 GitHub 下载摘要和包内文件校验，因此维护人员必须先验证过渡包的 GitHub 发布证明，再将其正式发布。安装过渡版后，后续更新会在本机验证发布证明。检查更新选中较新的正式版本后，若其更新包校验信息不完整，会停止并提示，不会悄悄安装较旧版本。

Windows、macOS 都采用相同流程。缺少发布验证工具时，系统自动从官方来源下载固定版本并核对校验值，安装在本机运行目录，无需管理员权限。下载或验证失败会停止升级；不能关闭验证来继续。

## 升级期间和失败处理

升级前会验证发布来源及兼容性，在副本中演练数据库迁移，备份数据库、底稿、历史模板及配置，然后进入维护状态并切换程序。请避开项目集中上传时段，保持服务器供电和联网。公网服务会暂停，升级后到“公网访问”重新生成链接。

提示失败时先保留整个安装目录、运行目录及备份。新版不会自动拿旧数据库覆盖升级后的新数据。“回退”只允许切换到兼容当前数据库和业务规则的程序；数据恢复须单独核对后操作。

## 发布者检查

每次变更都必须检查 Windows 和 macOS 的在线升级路径，包括保留账号、既有数据库、原始底稿、历史模板及原启动入口。不能仅验证全新安装。

1. 递增软件版本，确认完整迁移清单、允许升级的数据库版本及禁止回退的边界。
2. 在两个平台执行回归、干净包启动及旧版到新版的隔离升级检查。保留命令、结果和对应完整提交号。
3. 先创建草稿 Release；核对资产摘要和 GitHub 发布证明，再发布。检查未通过不得发布正式更新。
4. 现代业务版本发布时必须设置 `--latest=false`，保留过渡版为 GitHub latest，供旧更新器发现。现代更新器从正式版本列表选择最高版本。

   自动流程只创建草稿，不切换 latest。草稿下载和发布证明验证通过后，正式发布过渡版时使用 `gh release edit v2026.09.23.0 --draft=false --latest=true`，业务新版使用 `gh release edit v2026.09.23.1 --draft=false --latest=false`。最后核对 GitHub 的 `/releases/latest` 仍为过渡版，正式版本列表包含业务新版。
5. 新包由 `python -m scripts.build_system_release --policy docs/refactor/release-policy.json --output /absolute/path/budget-system-update.zip` 构建。过渡包由 `python -m scripts.build_legacy_bridge --output /absolute/path/bridge/budget-system-update.zip` 构建；二者格式和职责不同，禁止仅修改 schema 数字假装兼容。

GitHub 分发仅含代码和公开说明；数据库、上传预算、账号配置和验收中的业务资料不得入库或打包。
